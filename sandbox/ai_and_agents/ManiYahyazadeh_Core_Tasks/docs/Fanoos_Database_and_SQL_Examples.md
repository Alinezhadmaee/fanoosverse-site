# Fanoos Database and SQL Examples

*A separate practical reference for tables and queries*

This file contains examples only. Adapt names and constraints to the
real Fanoos schema before running anything on a shared or production
database.

## 1. Example table

A simple starting point for job posts:

``` sql
CREATE TABLE IF NOT EXISTS public.jobs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    source TEXT,
    source_job_id TEXT,
    title TEXT NOT NULL,
    company TEXT,
    city TEXT,
    job_type TEXT,
    salary_min NUMERIC,
    salary_max NUMERIC,
    description TEXT,
    status TEXT NOT NULL DEFAULT 'new',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

`BIGINT ... IDENTITY` creates an automatically increasing numeric ID.
`TEXT` stores text. `NUMERIC` stores numbers such as salary values.
`TIMESTAMPTZ` stores a timestamp with time-zone awareness. `NOT NULL`
means a value is required. `DEFAULT` supplies a value when none is
provided.

If source records can be imported more than once, consider a uniqueness
rule based on the source and source job ID:

``` sql
CREATE UNIQUE INDEX IF NOT EXISTS jobs_source_job_id_unique
ON public.jobs (source, source_job_id)
WHERE source IS NOT NULL AND source_job_id IS NOT NULL;
```

Only add this after checking existing data for duplicates.

## 2. Read data with SQL

``` sql
SELECT id, title, company, city
FROM public.jobs
WHERE status = 'new'
ORDER BY created_at DESC
LIMIT 20;
```

## 3. Insert a row

``` sql
INSERT INTO public.jobs (source, source_job_id, title, company, city)
VALUES ('example_site', 'abc-123', 'Python Developer', 'Example Co', 'Tehran')
RETURNING id, title, created_at;
```

## 4. Update a row

``` sql
UPDATE public.jobs
SET status = 'processed',
    updated_at = NOW()
WHERE id = 123
RETURNING id, status;
```

Always inspect the `WHERE` clause. Without it, an update may affect
every row.

## 5. Delete a row

``` sql
DELETE FROM public.jobs
WHERE id = 123
RETURNING id;
```

Treat deletes as destructive. Test with a `SELECT` using the same filter
first and make sure a backup exists for important data.

## 6. Add a column through a migration

Create a migration with the Supabase CLI, then put the SQL into the
generated file:

``` sql
ALTER TABLE public.jobs
ADD COLUMN IF NOT EXISTS employment_level TEXT;
```

Do not edit an already-applied migration to change history. Add a new
migration for later changes.

## 7. Add an index

If the application often filters jobs by status and sorts by creation
time, an index may help:

``` sql
CREATE INDEX IF NOT EXISTS jobs_status_created_at_idx
ON public.jobs (status, created_at DESC);
```

Indexes can speed up reads, but use disk and can slow writes. Add
indexes based on actual queries and check query plans.

## 8. Check a query plan

``` sql
EXPLAIN
SELECT id, title
FROM public.jobs
WHERE status = 'new'
ORDER BY created_at DESC
LIMIT 20;
```

`EXPLAIN ANALYZE` runs the query and reports actual timing; use it
carefully with queries that modify data because it really executes them.

## 9. Python client examples

Install:

``` bash
python -m pip install supabase python-dotenv
```

Read:

``` python
response = (
    supabase.table("jobs")
    .select("id, title, company")
    .eq("status", "new")
    .limit(20)
    .execute()
)
jobs = response.data
```

Insert:

``` python
response = (
    supabase.table("jobs")
    .insert({
        "source": "example_site",
        "source_job_id": "abc-123",
        "title": "Python Developer",
        "company": "Example Co",
        "city": "Tehran",
    })
    .execute()
)
```

Update one row:

``` python
response = (
    supabase.table("jobs")
    .update({"status": "processed"})
    .eq("id", 123)
    .execute()
)
```

The examples assume a `supabase` client has already been created. Keep
credentials in environment variables; never put privileged keys in
source code or Git.

## 10. Table design reminders

-   Use a primary key to identify each row.
-   Choose column types that match the data.
-   Use `NOT NULL` only when the value must always exist.
-   Use unique constraints or indexes when they match a real rule.
-   Avoid storing the same fact in many places unless there is a clear
    reason.
-   Store raw source data separately from cleaned/normalized fields when
    you need to preserve the original input.
-   Store processing status and timestamps if the pipeline needs retries
    and auditing.
-   Plan relationships between jobs, companies, and skills before
    duplicating complex data.
-   Enable and test access policies for tables exposed through Supabase
    APIs.
-   Run schema changes through migrations once the team adopts a
    migration workflow.
